# Установщик и обновления — решения (17.11.2026)

Как Barrens Voice ставится, обновляется и выпускается. Сделано в 0.4.0. Главные решения с альтернативами — в [docs/adr](adr/README.md): [0003](adr/0003-per-user-installer.md) (установщик), [0004](adr/0004-signed-updates.md) (обновления), [0005](adr/0005-separate-versions.md) (номера версий), [0006](adr/0006-dictionary-online.md) (словарь онлайн).

## Раскладка

Одна папка установки — всё внутри, чтобы выбор диска переносил все гигабайты (жёсткие ссылки из кэша uv работают только в пределах одного диска):

```
<папка установки>\        по умолчанию %LOCALAPPDATA%\BarrensVoice; мало места на C: — диск, где стоит WoW
  Barrens Voice.exe    запускатель с иконкой (installer/launcher.cs): запускает текущую версию; на него ведут ярлыки и автозапуск
  barrens-voice.install  метка: код по ней узнаёт, что он установлен
  uv.exe               ставит Python и библиотеки
  python\              Python из uv (python-build-standalone: в нём есть tkinter)
  app\0.4.0\           выпуск: companion\bv, addon\BarrensVoice, pyproject.toml, uv.lock и его .venv
  app\0.4.1\
  app\current\         junction на текущую версию (без прав администратора)
  data\                config.json, assignments.json, voices\, logs\, tmp\ — обновление не трогает
  cache\               кэш моделей (hf) и кэш uv
```

- Код находит свои папки через `bv/paths.py`: установлен (метка в корне, путь `app\<версия>\companion`) — `data\` и `cache\` установки; иначе — папка компаньона, как до установщика и в разработке. Переменные `BV_DATA`, `BV_CACHE`, `BV_STARTER` перекрывают это для тестов.
- Установка — для одного пользователя, без прав администратора (автозапуск через HKCU уже так и сделан).
- Ярлыки, автозапуск и перезапуск после обновления ведут на `Barrens Voice.exe` в корне установки — его видно в папке, у него иконка программы; он запускает `app\current` (`.venv\Scripts\pythonw.exe` и `companion\BarrensVoice.pyw` текущей версии). Это ~20 строк на C#, собранных компилятором .NET Framework, который есть в любой Windows 10/11. Он едет и в архиве выпуска: установка и обновление (`point_current`) кладут его в корень, если его нет или он изменился, а лаунчер при запуске проверяет это ещё раз — обновление, сделанное старой версией, его не клало.
- Переезд старой установки (папка с `BarrensVoice.cmd`) не делаем: чистая установка заодно проверит, что значения по умолчанию совпадают с рабочим `config.json`.
- Удаление спрашивает, удалять ли данные и кэш (модели — гигабайты). Установщик не запускается поверх работающего Barrens Voice (`AppMutex`).

## Python и библиотеки — uv

- Установленный компаньон ставится по `pyproject.toml` + `uv.lock` (проект, а не пакет в реестре: наш код ставится из папки версии). `requirements.txt` остался только для `BarrensVoice.cmd`, запуска из исходников.
- CUDA и DirectML — взаимоисключающие варианты (`[tool.uv] conflicts`): `--extra cuda` / `--extra directml`. Выбор — по видеокарте (NVIDIA → CUDA), без вопроса игроку; скрытый ключ `--runtime directml` — для проверки DirectML на NVIDIA.
- Обычный `onnxruntime`, который тянут RUAccent (и потом `piper-tts`), вычищается `override-dependencies`.
- `exclude-newer = "7 days"` в `[tool.uv]`: свежая версия пакета попадает к нам через неделю (защита от подменённых выпусков на PyPI); срочное исправление — исключением `exclude-newer-package`. У игрока установка с `--frozen` берёт версии из lock-файла и от срока не зависит.

## Обновление

- Новая версия ставится целиком в `app\X`: `uv sync --frozen --no-dev --extra …` с окружением в этой папке. Библиотеки берутся из кэша uv жёсткими ссылками — 1,9 ГБ CUDA не качаются заново, если их версия не менялась. Перед тем как стать готовой, версия проверяется своим же Python (`update.version_runs`, см. «Самопроверка версии» ниже) — не прошла, и версия не ставится. Потом `app\current` перенаправляется на неё: рядом создаётся `current.new`, старая ссылка переименовывается в `current.old`, новая — в `current`, при сбое всё возвращается назад (`install.point_current`; junction создаёт `_winapi.CreateJunction` — закрытый API CPython, — а если не вышло, `mklink /J`). Лишнее не нужно удалять по файлам: после первого удачного запуска новой версии остаются она и одна предыдущая (`install.prune`, в отдельном потоке — `.venv` версии — это тысячи файлов, и окно замирало), скачанные архивы удаляются сразу после подготовки. Удаляются только версии старше текущей: версия новее текущей — подготовленная или отвергнутая — остаётся (раньше оставлялась «самая новая по номеру», и брошенная тестовая сборка вытесняла подготовленную, после чего переключение вело в пустоту); остаются и `previous` из `update.json`, и то, на что указывают `current.new`/`current.old`. Версия сначала переименовывается в `<версия>.pruned`, потом удаляется: прерванное удаление не оставит полверсии под её именем, а остаток уберёт следующее (папку с открытым файлом Windows не переименует — она остаётся до следующего раза). Удаление идёт и через 5 с после каждого запуска лаунчера, если `update.json` нет: при «Закрываться вместе с игрой» лаунчер закрывается сразу после того, как версия принята, и удаление обрывалось. Удаляются только папки с именем версии (`VERSION_NAME`: чужая `backup` остаётся), `update.json` читается после `app\current` (обновление, применённое в этот момент, сохраняет свою `previous`), отвергнутая версия не считается «той, на которую вернуться» (`update-refused.json` хранит прежние отказы в `before`; старые лаунчеры читают только `version`). При откате отказ записывается до переключения; если предыдущей версии нет целиком, лаунчер один раз говорит, что вернуться не на что (`stuck` в `update.json`). `point_current` не направит `current` на папку без `install.STARTS` (`.venv\Scripts\pythonw.exe` и `companion\BarrensVoice.pyw` — то же, что проверяет `Starts` в launcher.cs), а лаунчер при запуске восстанавливает `current` из `current.new`/`current.old`, если переключение прервалось между двумя переименованиями (`install.repair_current`).
- Переключение под присмотром с самого начала: `data\tmp\update.json` (какая версия новая, какая была до неё, сколько раз упала) пишется **до** переключения `app\current`, через временный файл, а если переключиться не удалось — удаляется. Иначе ошибка после переключения (при удалении старой ссылки, при записи файла) оставила бы новую версию текущей без присмотра — откатиться было бы не по чему. Старая ссылка `current.old` после переключения удаляется по возможности, не вышло — уйдёт при следующем. Процесс, оборванный между двумя переименованиями, оставляет `current.new` и `current.old` без `current`: запускатель (`installer/launcher.cs`) тогда берёт `current.new`, затем `current.old` — ту, где есть `.venv\Scripts\pythonw.exe` и `companion\BarrensVoice.pyw`. `update.json`, который называет не ту версию, что сейчас в `app\current` (переключение не состоялось), лаунчер выбрасывает.
- uv: подписанный `manifest.json` называет uv выпуска (версия, адрес сборки для Windows на GitHub astral-sh/uv, SHA-256). Установленный `uv.exe` другой версии — обновление скачивает нужный, сверяет сумму из подписанного описания, собирает им окружение и после успешной сборки ставит на место старого; тот же — ничего не качается. Версия uv — `UV_VERSION` в `tools/release.py` (установщик берёт её оттуда же).
- Откат: новая версия не стартует (компаньон дважды падает при запуске) — лаунчер возвращает `app\current` на предыдущую и говорит об этом. Каждый конец компаньона новой версии — один из трёх исходов (`App.start_failed` → `update.record_start`):
  - ошибка в первые 60 с (`EARLY`) — неудачный старт, второй такой — откат;
  - код 0 или ошибка после 60 с — версия принята: `update.json` удаляется, старые версии удаляются; так же — когда компаньон работает дольше 60 с: лаунчер принимает версию сам, раз за запуск (`App.settle_running`), иначе компаньон, которого всегда останавливает лаунчер («Закрываться вместе с игрой» выключено), оставлял версию под наблюдением навсегда — ничего не удалялось, а откат через месяцы был возможен;
  - коды 3 (перезапуск с сетью), 4 (уже запущен другой компаньон), 5 (не читается `config.json`) и ошибка, которую компаньон объяснил сам (фаза `error` в `state.json`: нет аддона и т. п.), когда бы они ни случились, — ни то ни другое: `update.json` остаётся, ничего не удаляется, решает следующий запуск.
  > Считать такой конец удачным запуском нельзя: версия, первый запуск которой кончился кодом 3 (так и бывает без сети у выпуска с новой моделью), была бы принята, и её настоящие падения уже не откатывались бы. А версия, которая «объясняет» каждый свой запуск, так и не будет принята, и первое настоящее падение засчитается. `state.json` читается без сверки pid: `Companion.start` удаляет его перед каждым запуском, а в venv на Windows `python.exe` бывает прослойкой, которая запускает интерпретатор дочерним процессом с другим pid.
- Отказ: версию, с которой откатились или которая не прошла самопроверку, лаунчер помнит в `data\update-refused.json` (пишется через временный файл): плашка о ней остаётся, но сам он её больше не готовит — только по «Обновить», пока не выйдет версия новее. Отказ — только для этой самой версии: более старая ставится как обычно (тестер откатился с 0.5.0b1 на 0.4.1 и ушёл на стабильный канал — 0.4.2 придёт сама). И только проверка, которая запустилась и не прошла, отказывает: не смогла запуститься (таймаут, антивирус, медленный диск) — это обычная ошибка, следующая проверка попробует снова.
- Самопроверка версии — договор с каждым лаунчером, начиная с 0.4.0, его держит каждый выпуск. Лаунчер версии, стоящей до новой, запускает `<версия>\.venv\Scripts\python.exe -m bv.selfcheck` в папке `<версия>\companion`, если там есть `bv\selfcheck.py`. Код 0 — версия запускается, любой другой — отказ, а последняя строка stderr — причина (лаунчер пишет её в журнал: «обновление не удалось: версия … не запускается: …»; stderr просится в UTF-8). Что проверять, решает сам выпуск в `bv/selfcheck.py` (сейчас: tkinter, `bv.launcher.app`, `bv.__main__`, `bv.update` и ed25519 из cryptography — без них лаунчер не запустится и не обновится снова); неизменны только имя и место модуля и этот способ вызова. Версия без `bv/selfcheck.py` проверяется списком самого лаунчера (`update.FALLBACK_CHECK`, те же импорты). Выпущенные беты 1–13 никакой проверки не делают — 0.4.0 первый клиент, который её запускает.
- После обновления лаунчер перезапускает себя с ключом `--updated`: озвучка включается для запущенной игры, а сама игра не запускается (иначе «Запускать игру вместе с Barrens Voice» запустило бы её снова сразу после закрытия). Если лаунчер и так закрывался вместе с игрой, он переключает версию и закрывается без перезапуска.
- Не во время игры: версия готовится в фоне, переключение — при следующем запуске лаунчера или после закрытия игры (компаньон читает чат). Готовую версию можно поставить и сразу: «Установить сейчас» на плашке — компаньон останавливается, лаунчер перезапускается с новой версией и снова включает озвучку для запущенной игры (перерыв примерно на полминуты).
- Аддон в игре идёт за программой: отдельной проверки аддона нет, его новая версия приходит в выпуске программы (плашка пишет «и аддон X»). С «Обновлять автоматически» лаунчер сам заменяет аддон старше своего в каждой закрытой игре; запущенная — после её закрытия. Галочка выключена — только ссылка «обновить аддон». Аддон новее нашего (поставлен с CurseForge) не откатывается.
- Галочка «Обновлять автоматически» (по умолчанию включена). Выключена — лаунчер показывает «Вышла версия X — Что нового / Обновить», кнопка делает то же самое. Если протокол полоски у аддона и программы разный, компаньон говорит, что обновить — программу или аддон (`protocol.mismatch`, строка «Мост» в лаунчере). Поле `protocol` в `manifest.json` пока никто не читает.
- Проверка — при запуске лаунчера и раз в час. Стабильный канал — `releases/latest/download/manifest.json` (обычная загрузка, без лимита API); тестовый — список выпусков через API (60 запросов в час без входа). Стабильный канал не берёт тестовую сборку, даже если GitHub отдаст её как последнюю.
- Тестовый канал: выпуски GitHub с пометкой pre-release (тег вида `v0.5.0-beta.1`; CI помечает тег с дефисом сам). В настройках лаунчера — «Получать тестовые версии». Сняли галочку — остаёмся на тестовой до стабильной, которая новее (без отката). Установки beta 1–4 (их кода обновления нет в `tests/compat`) сравнивают версии только по числам (`version_key`): 0.4.0 для них старше их беты, и 0.4.0 они пропускают. Обновятся сами с 0.4.1 или более новой беты — или переустановкой. GitHub перечисляет выпуски по тексту тега (beta.9 раньше beta.10), а клиенты beta 1–10 берут первый выпуск списка с описанием: пока такие клиенты есть, старые тестовые выпуски удаляются, как только вышел следующий (с beta 11 берётся выпуск с наибольшей версией).

## Тесты обновления

Сломанное обновление ломает мод у всех — поэтому вся цепочка под тестами (`companion/tests/test_launcher.py`), и CI собирает выпуск только после них (на Windows: junction через `mklink`):

- `UpdaterFlow` — логика лаунчера (`bv.update.Updater`) против поддельного GitHub с выпусками, подписанными тестовым ключом: найти и подготовить, переключить только без игры и озвучки; одна и та же, более старая версия и своя бета — не обновление; чужая подпись и подменённый архив — отказ (и новая попытка в следующий раз); 404 — тихо; автообновление выключено — только сообщить, «Обновить» готовит; тестовый канал берёт новейший опубликованный выпуск с описанием, пропуская черновики и выпуски без описания; команда перезапуска.
- `Update`, `UvInPrepare`, `ReleaseUv`, `UvSyncFails`, `Starter`, `Install` — подпись, загрузка и сверка, откат после двух падений на старте, uv выпуска, запускатель, раскладка.
- `ReleaseBuild` — архив, который собирает CI (версия беты внутри, состав, описание сходится с архивом), ставится нашим установщиком.
- `OldClients` — новый выпуск ставится **кодом обновления, который уже стоит у игроков**: `companion/tests/compat/<версия>/` — неизменяемые копии `install.py` и `update.py` выпущенных версий. Изменили эти файлы в выпуске — положите рядом копию новой версии и добавьте её в тест. `test_every_release_has_its_copy` сверяет с копиями `update.py` и `install.py` каждого тега выпуска (кроме beta 1–4, они старше `compat`): оба файла изменились после beta 13, так что тегу 0.4.0 нужна `companion/tests/compat/v0_4_0/` и её тест в `OldClients`.

## Версии

- Совместимость решает номер протокола полоски (сейчас 1), а не номера версий: аддон пишет его в каждом кадре, компаньон читает версии из `protocol.SUPPORTED`. Новый протокол оставляет в `SUPPORTED` предыдущий: компаньон, обновлённый посреди игры («Установить сейчас», старый аддон до `/reload`), и аддон, обновлённый раньше программы, продолжают работать. Кадр протокола, которого компаньон не читает, он не принимает за перекрытую полоску: через 3 секунды пишет, что обновить — программу («аддон новее Barrens Voice») или аддон («аддон старше… /reload»), лаунчер показывает это в строке «Мост».
- Один выпуск (тег `vX.Y.Z`) на весь проект, одна история изменений. Версия аддона в `.toc` поднимается, только если менялся сам аддон, — тогда лаунчер не просит `/reload` из-за правок одного компаньона. Выпущенная версия аддона неизменна: один номер — одно содержимое во всех выпусках, тестовые тоже. Изменили аддон после выпуска — поднимите `## Version` до следующего; тест `AddonVersion` сверяет аддон со всеми тегами, где был тот же номер (в beta 1–9 под номером 0.3.0 уходил уже другой аддон, и лаунчер его не обновлял). Тестовые сборки несут тестовые сборки аддона — `0.4.0b1`, `0.4.0b2`… (номер растёт, только когда меняется аддон, и не обязан совпадать с номером беты программы), а выпуск — его чистый номер: лаунчер считает `0.4.0b2 < 0.4.0`, так что выпуск заменяет бету у тестеров. `tools/release.py` не соберёт выпуск без беты с бета-аддоном. В игре бета показывается как «0.4.0 beta 1», а строка «что нового» — от её выпуска.
- Номера версий даются при выпуске; в README — этапы (Roadmap), а не версии.

## Выпуск (CI)

- Каждый шаг CI — задача mise (`mise run test`, `mise run build`, `mise run installer`…), которая так же запускается локально; workflow GitHub только ставит mise (`jdx/mise-action`) и вызывает эти задачи. Действия закреплены по SHA коммита, а не по тегу (в заданиях есть ключ подписи), у `ci.yml` права по умолчанию — только чтение. Задание словаря онлайн не публикует ревизию старше той, что уже в ветке, и не идёт в два потока. Выпуск предупреждает, если у другого выпуска (кроме последнего стабильного) ещё лежит `manifest.json` — см. тестовый канал выше. Установщик (Inno Setup) собирается только на Windows: локально — на тестовой машине.
- GitHub Actions, только раннер Windows (компаньон — только для Windows; стандартные раннеры бесплатны для публичных репозиториев): тесты Python и Lua на каждый push.
- На тег: архив `barrens-voice-X.Y.Z.zip` (код, аддон, `pyproject.toml`, `uv.lock`, `news.toml`), `manifest.json` (версия, протокол, версия аддона, SHA-256) с подписью ed25519 (публичный ключ — в лаунчере, закрытый — в секретах CI), установщик (Inno Setup), выпуск на GitHub с описанием из записи «Что нового» (`news.toml`, по-русски) и ссылкой на CHANGELOG.
- Загрузки на CurseForge и Wago в CI пока нет — это этап «CurseForge и Wago» (ниже): только когда менялся аддон, упаковщик BigWigs, `.pkgmeta`. У Forever на CurseForge своя версия игры (1.60.1). Аддон, которому нужна внешняя программа, на CurseForge допустим: так устроены ForeverDubbed и AI Agents Chat.
- Словарь онлайн (сделано): после тестов на master CI собирает `dictionary.json` (`mise run dictionary`: стандарт и `D.RENAMED` из `Dictionary.lua`, формат, ревизия — время последнего коммита, менявшего `Dictionary.lua`), подписывает ключом выпусков и кладёт в ветку `dictionary`, только если словарь изменился. Компаньон читает его с `raw.githubusercontent.com/rgeraskin/barrens-voice/dictionary/dictionary.json` при запуске и раз в час. Подробно — DEVELOPMENT, «Словарь на слоях».

## Подпись установщика

- После этапа «CurseForge и Wago»: бесплатный SignPath Foundation для open source (MIT, публичный репозиторий, сборка в GitHub Actions, двухфакторная защита, раздел «Code signing policy» в README). Издателем в Windows будет «SignPath Foundation». Каждый выпуск подтверждается вручную — их условие (щелчок в письме или через их API, не из CI).
- Спросить в заявке: модели (F5, CC BY-NC) в установщик не входят и скачиваются отдельно — проходит ли это требование «без проприетарных компонентов».
- SmartScreen может предупреждать и с подписью, пока у файла нет репутации.

## Этап «CurseForge и Wago»: что уже известно

- **CurseForge узнаёт установленный аддон по отпечаткам файлов, а не по `## Version`.** Файлы, не совпавшие ни с одним загруженным файлом, — «Modified», и такой аддон CurseForge сам не обновляет (защищает правки). Отсюда:
  - В архиве выпуска должен лежать ровно тот аддон, что уходит на CurseForge, — байт в байт, после их упаковщика (BigWigs packager: подстановки вроде `@project-version@`, исключения из `.pkgmeta`). Проще всего класть в архив сам собранный упаковщиком zip, а не папку из git.
  - Номера раздельные (программа — `pyproject.toml`, аддон — `.toc`), не единый: при едином номере `.toc` меняется с каждым выпуском программы, и пришлось бы выкладывать на CurseForge аддон без изменений при каждом выпуске — иначе после обновления программы он у игрока «Modified» и CurseForge перестаёт его обновлять.
  - Лаунчер может поставить версию раньше, чем CurseForge одобрит файл: до одобрения аддон у игрока «Modified», после — совпадёт.
  - Загрузка на CurseForge и Wago — только когда изменился аддон (у тега, где поднят `## Version`).
- **Тестовые сборки аддона** (`0.4.0b1`…) — файлом типа beta на CurseForge, выпуск — release. Выпуск программы не собирается с бета-аддоном (`tools/release.py`).
- **Описание изменений для CurseForge** — только про аддон: выжимка из общего CHANGELOG.md. Пункты, касающиеся аддона, нужно будет как-то помечать, чтобы собирать её автоматически.
- **Установщик**: без подписи Windows показывает SmartScreen «Windows защитила ваш компьютер» (проверено на beta 6) — подпись в разделе выше. Прямая ссылка `releases/latest/download/BarrensVoice-Setup.exe` в README заработает с первым выпуском без беты: GitHub не отдаёт по `latest` тестовые сборки.

## Когда-нибудь

- **Установка для всех пользователей Windows** (семейный компьютер): программа в Program Files и общий кэш моделей в `C:\ProgramData\BarrensVoice` — с правом «изменение» для всех пользователей, которое выдаёт установщик с правами администратора. Без такого права второй пользователь не может обновить или докачать модель (кэш Hugging Face пишет файлы блокировки). Жёсткие ссылки тут не помогают: они работают только в пределах одного диска, а папка данных может быть на другом. Автообновление в Program Files — через UAC или отдельную службу.
  - **Может хватить и нынешнего установщика.** Только для того, кто ставил, он создаёт ярлыки, запись в «Приложениях» и автозапуск (`HKCU`). Сама папка установки на несистемном диске доступна всем: на тестовой машине у папки установки на втором диске и всего внутри право «изменение» для «Прошедших проверку» (любой вошедший пользователь), унаследованное от корня диска (`icacls`, 17.11.2026). Значит, второй пользователь, скорее всего, может запускать `Barrens Voice.exe` оттуда и даже обновлять. Тогда «для всех» — это ярлыки и автозапуск для каждого (например, их создаёт первый запуск лаунчера у нового пользователя) и раздельные настройки: `data` у каждого свой, `cache` с моделями общий. Не проверено: запуск и обновление от второго пользователя, два пользователя одновременно (два лаунчера, один `app\current`). Установка в `%LOCALAPPDATA%` (по умолчанию) так не работает: профиль пользователя закрыт для других.
  - **RedirectionGuard.** Установщик для одного пользователя собран с `RedirectionGuard=no`: защита Inno Setup наследуется всем, что он запускает (флаг `runasoriginaluser` без прав администратора не помогает), а установка состоит из junction — Python от uv (`cpython-3.13` → `3.13.x`) и наш `app\current`; через них uv и Python падали с ошибкой 448 «untrusted mount point» (beta.1, beta.2). Выключить там можно: защита нужна установщикам **с правами администратора**, которых junction, подложенная обычным пользователем, уводит писать в чужие места, а этот ставит в папку того же пользователя от его же имени. Установщик для всех пользователей будет с правами администратора — в нём защиту **не выключать**: junction должен создавать сам процесс с правами администратора (их Windows доверяет), а шаги, которым нужны junction, созданные обычным пользователем, — запускать без повышения прав.
- **Один движок для всех.** Если Piper (docs/piper.md) окажется не хуже F5, значение по умолчанию `"engine": "auto"` начнёт выбирать Piper и на NVIDIA — пользователи получат его обычным обновлением. Тогда сборки с CUDA и DirectML нужны только тем, кто сам выберет F5, и установщик становится маленьким. Значение по умолчанию хранить как `"auto"` и решать при запуске: `load_config` записывает значения по умолчанию в `config.json`, и новое значение иначе не дошло бы до старых установок.

## Windows-выпуски форка

При сборке релиза в форке упаковщик использует репозиторий из `GITHUB_REPOSITORY`. Переменная репозитория `BV_UPDATE_PUBLIC_KEY` содержит открытый ключ этого форка в base64. Секрет `BV_SIGNING_KEY` содержит соответствующий приватный ключ. Собранный лаунчер ищет подписанные выпуски в том же форке. Обновления словаря по-прежнему проверяются ключом проекта, который их публикует.

Для перехода с исходного Barrens Voice запустите установщик из форка и выберите прежнюю папку установки, если мастер её не подставил. Существующие данные и кэш используются из этой папки. После установки откройте Barrens Voice привычным ярлыком. Обновление аддона доступно из карточки WoW. Если игра запущена, после обновления аддона примените его командой `/reload`.

Ключ манифеста проверяет содержимое пакета автообновления. Authenticode установщика требует отдельного сертификата Windows.
